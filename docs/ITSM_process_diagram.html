Stage codes: 1.1 … 6.1 = main pipeline. X = exception/edge flows. S = scheduled (Recurrence). T = helper/tool. Z = retired/off. Lane tags [Request] / [Incident] / [Both] / [OFF] taken from FlowDocsInventory.

* 3.1 Approval-Bridge lane: the inventory currently tags it [Incident], but the flow definition shows it polls the Approvals SharePoint list and processes any terminal approval — and the Approvals list is fed by both RITM-Approval (Request) and Triage-Orchestrator's inline approval (Incident). Functionally it services both lanes, so the diagram tags it [Both]. Confirm whether the inventory should be updated.

How it really works: the Validator does NOT call the lanes — it PATCHes the row. 2.2 RITM-Generator and 2.1 Triage-Orchestrator each poll Tickets on their own trigger. When the Validator cannot type a ticket it fires the 1.2 Clarifier (HTTP, fire-and-forget) which asks the caller via an Approvals card and PATCHes the chosen type back, reopening the row. Executors are SIBLINGS polling Provisioning Jobs by JobType — not a call chain.

AI surface area: AI Builder GPT in 3.2 RITM-Validation-Triage · cre79_agent in 2.1 Triage-Orchestrator & X1 Major-Incident-Detector · T1 SearchKnowledgeBase Copilot Studio skill. The Clarifier (1.2) is deterministic — not AI.
